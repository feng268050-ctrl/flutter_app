## ADDED Requirements

### Requirement: Inbound upload command triggers list upload pipeline

When the device receives a WebSocket frame with `type` `command.upload_video` and a valid unified envelope, the client SHALL parse `payload.videoId` as a non-empty string. The client SHALL resolve that value to at most one local row in `t_params_process_video` by the column `videoId`. If a row exists and the command is accepted per conflict and eligibility rules in this capability, the client SHALL start the **same** monitor-list video upload implementation used when the user starts upload from the process **Videos** list (metadata when applicable, then STS video upload via `MonitorProcessVideoListUploadRunner` or its direct successor in code). If no row exists, `videoId` is missing or blank, or the command cannot be honored, the client SHALL NOT start that pipeline for this command.

#### Scenario: Known videoId starts the shared runner

- **WHEN** the server sends `command.upload_video` whose `payload.videoId` equals the `videoId` of a persisted local process video row and no applicable conflict or eligibility rule forbids starting
- **THEN** the client MUST invoke the same upload entry path as the list **Upload** action for that row’s primary key after resolution from `videoId`

#### Scenario: Unknown videoId does not start upload

- **WHEN** the server sends `command.upload_video` with a `videoId` that does not match any local row
- **THEN** the client MUST NOT start the upload pipeline for that command and MUST send `command.upload_video_ack` with `data.success` false and a non-empty `data.message` describing the failure

### Requirement: Progress dialog when Videos UI is active

When a `command.upload_video` starts the monitor-list upload pipeline and the monitor **Videos** list is the current user-visible surface (the same context where a manual **Upload** would present progress UI), the client SHOULD show the same upload progress presentation as manual **Upload** (including cancel affordance if the manual path exposes it) and drive it from the runner callbacks. When that Videos context is not active, the client SHALL NOT require a progress dialog for the upload to proceed.

#### Scenario: User on Videos tab sees progress

- **WHEN** the user is on the process **Videos** tab and a valid `command.upload_video` starts an upload for a resolved row
- **THEN** the client SHOULD show the same progress UI behavior as when the user taps **Upload** for that flow

#### Scenario: User not on Videos tab runs without dialog

- **WHEN** the process **Videos** tab is not the active user-visible context and a valid `command.upload_video` starts an upload
- **THEN** the client MUST still run the upload pipeline and MUST NOT depend on showing `VideoUploadProgressDialog` (or equivalent) for correctness

### Requirement: Ack correlation and payload shape

For every inbound `command.upload_video` frame the device attempts to handle (including failures before starting upload), the device SHALL send exactly one corresponding `command.upload_video_ack` frame on the same WebSocket unless the connection is lost before send. The outbound frame SHALL use the unified envelope with a **new** top-level `id` generated by the device. The outbound `payload` SHALL be a JSON object containing:

- string field `request_id` whose value equals the top-level `id` of the inbound `command.upload_video` frame
- object field `data` containing boolean field `success` and string field `message` (empty string allowed when `success` is true)

#### Scenario: Ack request_id matches inbound id

- **WHEN** the device completes handling of an inbound `command.upload_video` whose top-level `id` is `cmd-1`
- **THEN** the client MUST send `command.upload_video_ack` whose `payload.request_id` equals `cmd-1` and whose top-level `id` is not `cmd-1`

#### Scenario: Failure carries message

- **WHEN** the device sends `command.upload_video_ack` with `data.success` false
- **THEN** `payload.data.message` MUST be a non-empty human-readable explanation

### Requirement: Ack does not wait for upload completion

The device SHALL send `command.upload_video_ack` based on whether the **command** was executed successfully (validation, conflict checks, and handoff to the upload runner), and MUST NOT delay the ack until the video file upload completes, fails, or reaches a terminal `video.uploading` state.

#### Scenario: Success ack without terminal upload state

- **WHEN** the upload pipeline has been started successfully for the command
- **THEN** the client MAY send `command.upload_video_ack` with `data.success` true before multipart upload completion

### Requirement: Single active list upload runner

The client SHALL maintain at most one active monitor-list foreground upload runner for this coordination scope (the same `MonitorProcessVideoListUploadRunner` family used by the Videos list). When an accepted `command.upload_video` starts an upload while another upload is already active, the client SHALL cancel or supersede the prior runner in the **same** way as when the user taps **Upload** on a different row while one is in progress (see `ProcessVideoViewModel.startMonitorListForegroundUpload`), then start the new upload. The client MUST NOT run two concurrent monitor-list foreground upload runners.

#### Scenario: New command supersedes in-flight list upload

- **WHEN** a monitor-list foreground upload is already in progress and a new `command.upload_video` is accepted and starts an upload for a resolved row
- **THEN** the client MUST stop or replace the prior runner per the same policy as the list **Upload** action and MUST start exactly one new runner for the commanded row
