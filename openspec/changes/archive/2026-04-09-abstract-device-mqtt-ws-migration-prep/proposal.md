## Why

当前设备数据上报与指令下发逻辑直接耦合 MQTT 实现，导致业务处理与传输协议绑定，后续迁移 WebSocket (WS) 风险高、改动面大。现在先完成协议抽象层与统一处理模型，可以在保持现有 MQTT 运行的同时，为 WS 平滑切换打基础。

## What Changes

- 新增统一的设备消息通道抽象，解耦“设备业务语义”与“MQTT 传输细节”。
- 为设备数据上报建立标准化入口：把原始 MQTT 上报统一映射为内部标准事件/数据模型。
- 为下达指令建立统一处理链路：命令构建、路由、发送、回执处理使用一致接口，屏蔽协议差异。
- 引入协议适配器分层：先实现 MQTT 适配器，并预留 WS 适配器接入点与切换策略。
- 补充迁移保护机制（可观测性、错误分类、回退策略）以降低未来 WS 上线风险。

## Capabilities

### New Capabilities
- `device-data-channel-abstraction`: 定义设备数据上报的统一抽象与标准事件模型，确保上层处理不依赖 MQTT。
- `device-command-channel-abstraction`: 定义设备指令下发与回执处理的统一抽象，支持后续从 MQTT 平滑扩展到 WS。

### Modified Capabilities
- （无）

## Impact

- 设备通信相关服务层与消息处理流程（上报解析、命令下发、回执处理）将重构为抽象接口 + 协议适配器。
- MQTT 相关 topic/订阅与发布调用将下沉到 MQTT 适配器，不再散落在业务处理代码中。
- 新增内部标准事件与命令模型，影响日志、监控与错误处理路径。
- 对外业务 API 预期不变，但内部接口会新增协议无关层，后续引入 WS 时可复用同一业务逻辑。
