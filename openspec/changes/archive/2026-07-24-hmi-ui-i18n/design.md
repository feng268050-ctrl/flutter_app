## Context

`persist-common-settings-json` already stores Language (`EN`/`ZH`) and applies it to CyberIME. Product UI strings remain English literals. Operators selecting 中文 do not see a Chinese HMI.

**Sources of truth for this change:**

| Concern | Source |
|---------|--------|
| Flutter i18n architecture + host commands | Sibling `lasercyber-mobile` (`gen-l10n`, parent–child ARBs, `make l10n*`, OpenCC zh_TW sync) |
| Product copy for on-device HMI features | Sibling `lws-ui` `app/src/main/res/values{,-en,-zh}/strings.xml` (~984 keys EN/ZH) |
| Persistence / IME hook | Existing `CommonSettingsStore` + `AppCyberImeLanguageProvider` in `app/hmi/` |

lws-hmi targets Flutter **3.24.4**. Mobile’s ARBs are cloud-app UI and are **not** the primary copy source.

## Goals / Non-Goals

**Goals:**

- Ship Flutter `gen-l10n` in `app/hmi/` with Mobile-parity parent–child ARB workflow and `make l10n` / `l10n-sync` / `l10n-gen` / `l10n-verify`.
- Drive `MaterialApp` locale from Common Settings so UI rebuilds when Language changes.
- Localize **already-implemented** product surfaces (Settings shell + sub-pages, Advanced Settings, Device Info, Monitor, alarms/warn dialogs, boot self-check, Home chrome) using lws-ui EN/ZH where keys exist; translate HMI-only gaps.
- Support runtime locales `en-US`, `zh-CN`, `zh-TW` (zh_TW via OpenCC + optional manual overrides), matching Mobile tooling while keeping Language Settings endonyms.

**Non-Goals:**

- Imperial unit conversion / display scaling (Unit pref remains store-only for conversion).
- Completing CyberIME ChineseGlobal assets/layout (IME mapping stays; package gap documented elsewhere).
- Full localization of `packages/cyber_ui` / `cyber_ime` internals.
- P2 Demo / hidden engineering surfaces as first-class priority.
- Importing lasercyber-mobile cloud ARB keys wholesale.
- Backend `Accept-Language` HTTP (no product cloud API equivalent on device HMI).

## Decisions

### D1 — Flutter official gen-l10n (not easy_localization)

**Choice:** `flutter_localizations` + `flutter: generate: true` + `l10n.yaml` → `AppLocalizations`, same as Mobile.

**Alternatives:** easy_localization / GetX — rejected to stay aligned with Mobile and Flutter pin.

### D2 — Parent–child ARB layout + OpenCC zh_TW

**Choice:** Human-edited parents `app_en.arb` (template + `@metadata`) and `app_zh.arb` (Simplified). Children `app_en_US.arb` / `app_zh_CN.arb` (locale stubs) and `app_zh_TW.arb` (diff overrides) generated by adapted `sync_l10n_child_arbs.py` + vendored OpenCC data.

**Rationale:** Matches Mobile commands; lws-ui has no Traditional Chinese, so zh_TW starts as OpenCC of zh with room for product-term overrides later.

### D3 — Copy workflow from lws-ui, not Mobile ARBs

**Choice:** For each implemented HMI feature, map lws-ui `snake_case` keys → ARB `lowerCamelCase`. Prefer lws-ui EN/ZH verbatim. If lws-ui lacks a string for an HMI-only label, author EN + ZH in parents.

**Key mapping rule:** `common_settings_group_display_sound` → `commonSettingsGroupDisplaySound`; Android `%1$s` → ARB `{name}` placeholders with `@metadata` only in `app_en.arb`.

**Priority namespaces (implemented features):** settings chrome, language/units, wifi/network/bluetooth, device info, alarms (~142 keys), boot self-check, monitor/home chrome, advanced settings, confirm/cancel globals. Defer unused engineer-process / AI-vision-heavy blocks until those HMI flows ship.

### D4 — Locale wire values migrate to BCP-47 with legacy read

**Choice:** Persist `language` as `en-US` | `zh-CN` | `zh-TW`. On read, map legacy `EN`→`en-US`, `ZH`→`zh-CN`. Default `en-US`. Language Settings shows endonyms (English / 简体中文 / 繁體中文).

**IME mapping:** `en-US` → EnglishGlobal; `zh-CN` / `zh-TW` → ChineseGlobal (same as today’s ZH→chinese).

**Alternatives:** Keep `EN`/`ZH` only — rejected because Mobile tooling and lws-ui runtime tags are BCP-47; three-locale UI needs distinct store values.

### D5 — MaterialApp locale driven by CommonSettingsStore

**Choice:** Wrap `MaterialApp` so `locale` / `supportedLocales` / `localizationsDelegates` follow the store; rebuild on `notifyListeners()`. Consumption: `AppLocalizations.of(context)!` (+ feature `extension … on AppLocalizations` for enum/code maps).

### D6 — Alarm catalog uses localization keys

**Choice:** Keep `cyber_alarm` catalog model with title/body **keys** (or code→l10n resolver in App). Resolve strings via `AppLocalizations` at presentation time. Seed from lws-ui `*_alarm_title` / `*_alarm_content`. Do not put full bilingual literals only in Dart maps without ARB.

### D7 — Host tooling paths

**Choice:** Adapt Mobile scripts into `scripts/flutter/` with `APP_DIR=app/hmi`. Add root Makefile targets `l10n`, `l10n-sync`, `l10n-gen`, `l10n-verify`. Prefer pinned `flutter-sdk/bin/flutter` when present (same as other HMI scripts). Commit generated `app_localizations*.dart`. Document in README / AGENTS.md.

### D8 — Phased string migration (implementation order)

1. Scaffold + MaterialApp + Language page + store migration  
2. Settings shell + Common/Advanced/Device Info pages  
3. Alarms + warn dialogs  
4. Monitor + boot self-check  
5. Home chrome (+ ZH text assets or Text replacements for mode labels)  
6. Remaining implemented Wi‑Fi / IP camera / process library chrome  

Each phase: add ARB keys → `make l10n` → replace literals → analyze/tests.

## Risks / Trade-offs

- [Large string surface (~600–900 literals)] → Mitigate with phased tasks; prioritize Settings + alarms; track remaining English with a short checklist in tasks.  
- [lws-ui vs HMI wording drift] → Prefer lws-ui copy; document intentional HMI-only differences in ARB comments sparingly.  
- [zh_TW quality from OpenCC] → Accept auto conversion; allow manual overrides in `app_zh_TW.arb` like Mobile.  
- [Legacy `EN`/`ZH` on field devices] → Normalize on read; next write upgrades wire value.  
- [Home English WebP labels] → Prefer Text + l10n over new bitmap assets when layout allows; otherwise add `_zh` assets.  
- [Incomplete migration leaves mixed language UI] → Language footer MUST NOT claim IME-only once UI locale ships; incomplete areas stay English until their phase lands (document in release notes / tasks).  
- [Flutter 3.24.4 gen-l10n quirks] → Validate with pinned SDK only; do not assume newer Material l10n APIs.

## Migration Plan

1. Land scaffold + tooling + store BCP-47 + MaterialApp wiring (UI still mostly English).  
2. Migrate surfaces phase-by-phase; run `make l10n-verify` before analyze/CI.  
3. On device: existing `language: "ZH"` continues to mean Simplified after warm-read remap.  
4. Rollback: revert App commit; leftover BCP-47 JSON remains readable if store keeps accepting both forms (forward-compat on older builds is not required).

## Open Questions

- None blocking: zh_TW is included for Mobile command parity; if product later wants EN/ZH-only Settings UI, hide zh_TW option without dropping tooling.
