## ADDED Requirements

### Requirement: Worker presigned-put discovery uses the same host as device WebSocket

The system SHALL derive the Worker API hostname for presigned uploads from `DeviceWebSocketConfig.resolveApiHost()` (production host when `BuildConfig.RELEASE_CHANNEL` is true, otherwise the non-release test host), and SHALL construct the presign endpoint as `https://` + that hostname + `/upload/device/presigned-put`.

#### Scenario: Release channel uses production Worker host

- **WHEN** the application build has `RELEASE_CHANNEL` true
- **THEN** presigned-put requests SHALL use hostname `api-prod.lasercyber.workers.dev`

#### Scenario: Non-release channel uses test Worker host

- **WHEN** the application build has `RELEASE_CHANNEL` false
- **THEN** presigned-put requests SHALL use hostname `api-test.lasercyber.workers.dev`

### Requirement: Presign request query parameters and object key layout

The system SHALL call the presign endpoint with HTTP GET and the following query parameters: `sn` (device serial), `content_type` (MIME type of the video file), `file_name` (file base name or safe filename chosen for storage), and `key` whose value SHALL be `uploads/devices/{sn}/{date}/{file_name}` where `{sn}` matches the `sn` query parameter, `{file_name}` matches the `file_name` query parameter, and `{date}` is a calendar date string generated by the client in a single agreed format used consistently for the lifetime of the change (documented in implementation).

#### Scenario: Key includes device segment

- **WHEN** presign is requested for serial `ABC` and filename `clip.mp4`
- **THEN** the `key` parameter SHALL begin with `uploads/devices/ABC/` and SHALL end with `/clip.mp4`

### Requirement: ApiResult JSON is parsed for every HTTP status

The system SHALL read the presign response body as UTF-8 text whenever a response body is present, and SHALL attempt to deserialize it into the `ApiResult` shape with fields `code` (number), `success` (boolean), `data` (object or null), and `message` (string or null). This deserialization attempt SHALL run for presign responses regardless of the HTTP status code (including non-2xx). If JSON parsing fails, the system SHALL treat the presign call as failed and SHALL include the HTTP status and/or raw body snippet in diagnostic logs.

#### Scenario: HTTP 400 with JSON body still drives client error

- **WHEN** the presign HTTP response status is 400 and the body is valid JSON with `success` false and `message` set
- **THEN** the client SHALL surface the logical failure using `message` and SHALL not assume failure solely from the HTTP status without inspecting the parsed result when JSON is valid

#### Scenario: HTTP 200 with success false is a logical failure

- **WHEN** the presign HTTP response status is 200 and the JSON has `success` false
- **THEN** the client SHALL treat the operation as failed and SHALL prefer `message` for user-visible or callback error text

### Requirement: Successful presign payload fields

When `success` is true and `data` is non-null, the system SHALL require `data.upload_url` (non-empty string), `data.method` equal to `PUT` ignoring case, and SHALL use `data.expires_in_seconds` as a hint for upload timeout upper bounds where the implementation schedules a bounded upload. The system SHALL retain `data.public_url` and `data.key` for subsequent metadata registration or logging.

#### Scenario: Valid presign enables PUT upload

- **WHEN** `success` is true and `data` contains a non-empty `upload_url` and `method` `PUT`
- **THEN** the system SHALL initiate an HTTP PUT of the local video bytes to `upload_url` with `Content-Type` equal to the `content_type` query parameter sent to presign

### Requirement: Video bytes upload via presigned PUT

The system SHALL upload the selected local video file to `upload_url` using HTTP PUT. The request SHALL include the `Content-Type` header matching the presign `content_type` parameter. The system SHALL stream the file from storage without loading the entire file into memory.

#### Scenario: PUT returns success

- **WHEN** the PUT completes with an HTTP status in the 2xx range
- **THEN** the system SHALL treat the object upload as successful and SHALL proceed to any configured follow-up step (for example metadata submission to business APIs)

#### Scenario: PUT returns non-success

- **WHEN** the PUT completes without a 2xx status
- **THEN** the system SHALL treat the upload as failed and SHALL not claim the video is available at `public_url` for downstream steps
