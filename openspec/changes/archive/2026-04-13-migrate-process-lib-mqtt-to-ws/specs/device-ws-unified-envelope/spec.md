## ADDED Requirements

### Requirement: Inbound process library command envelope

Frames with `type` equal to `command.send_process_lib` SHALL use the unified WebSocket JSON envelope (`v`, `type`, `id`, `ts`, `payload`). The `payload` object SHALL contain the process-library content in a shape the device can map to the same persistence model used for the legacy MQTT `PROCESS_LIB` ingest path (**ProcessLibrary** aggregate: version metadata and ordered process-parameter rows / `dataList` semantics as implemented in `ServerPushMessageHandler.saveProcessLibrary` today). **ProcessLibrary** is the normative domain name for this aggregate; the reference app SHALL implement it with the Java type **`ProcessLibrary`** (renamed from `ProcessVersion`; see `device-data-channel-abstraction` delta in this change).

#### Scenario: Command frame structure

- **WHEN** the server sends a `command.send_process_lib` message on the device WebSocket
- **THEN** the frame MUST include top-level `v`, `type`, `id`, `ts`, and object `payload`, with `type` equal to `command.send_process_lib`, and MUST NOT place process-library business fields outside `payload`

### Requirement: Outbound process library acknowledgement

After the device completes handling of an inbound `command.send_process_lib` frame (including persistence or application-defined handling that finishes the request), the device SHALL send a WebSocket frame with `type` `command.send_process_lib_ack`. The outbound frame SHALL use a **new** top-level `id` generated by the device for that outbound message (per outbound message identity rules elsewhere in this capability). The outbound `payload` SHALL be a JSON object containing:

- string field `request_id` whose value equals the top-level `id` of the inbound `command.send_process_lib` frame
- numeric field `code` using the same success/failure numeric convention as `command.send_process_param_ack` (`200` for success, `500` for failure unless a project-wide standard supersedes)
- string field `message` (human-readable result; empty string allowed)

#### Scenario: Ack uses new message id

- **WHEN** the device receives `command.send_process_lib` with top-level `id` `server-lib-1`
- **THEN** the device MUST send `command.send_process_lib_ack` whose top-level `id` is newly generated for that ack and MUST NOT reuse `server-lib-1` as the outbound `id`

#### Scenario: Ack payload carries result details

- **WHEN** the device sends `command.send_process_lib_ack` in response to an inbound command whose top-level `id` is `server-lib-1`
- **THEN** `payload` MUST include `request_id` equal to `server-lib-1`, a numeric `code`, and string `message`
