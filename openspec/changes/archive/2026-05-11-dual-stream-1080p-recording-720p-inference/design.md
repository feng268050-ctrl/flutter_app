## Context

AI Vision 当前链路主要基于 EasyDarwin `EasyPlayerClient` + `TextureView`，同一 RTSP 码流既服务实时显示/推理也服务录制。近期已通过低延迟队列与限频降低整体延迟与花屏，但在连续移动场景仍有停顿。若摄像头支持子码流，采用双码流分工：**录制保持 1920×1080（主流）**；**实时/推理走子码流**。现场 IPC 参考配置为子码流 **640×512**、**H.264 Baseline**、**768K CBR**、帧率必选、I 帧间隔偏小（见 `docs/dual-stream-workflow.md`）。原先文档中的 **1280×720** 仍是可行的备选子码流分辨率；验收以 IPC 实际输出与 `RESULT_VIDEO_SIZE` / `LIVE_VIDEO_SIZE` 日志为准。

## Goals / Non-Goals

**Goals:**
- 实时链路（预览+推理）使用 **独立子码流**，分辨率由 IPC 配置决定；现场目标为 **640×512** 一类低负载配置以降低运动场景停顿感（可选更高如 720p，以实测为准）。
- 录制链路保持 1920×1080，不降低留档质量。
- 支持摄像头有子码流时的双码流主/子流选择；不支持时提供可预期降级。
- 明确 640x640 仅用于模型输入前处理，不作为默认摄像头输出目标。

**Non-Goals:**
- 本期不强制切换到 FFmpeg+MPP 全新播放器架构。
- 本期不修改模型训练流程与标签体系，仅约束运行时输入处理。

## Decisions

1. **双码流优先，单码流降级**  
   - 优先使用主码流（1080p）给录制，子码流（如 **640×512** 或 720p，由 IPC 配置）给实时预览/推理。  
   - 若摄像头不支持子码流或子流不可达，降级到单路主流或单路降分辨率策略（实时优先），同时保留录制功能（可按现场策略选择同流录制或回退主流录制）。

2. **分辨率控制分层**  
   - 摄像头输出分辨率由 IPC 流配置决定（RTSP URL/相机参数），不是简单改 App 常量。  
   - AI 推理输入可独立做 letterbox 到 640x640；显示/解码保持 16:9，避免画面比例失真。

3. **配置与可观测性**  
   - 在 `CameraConfig` 增加主/子流 URL 或 profile 配置能力（默认主流 `/PR0`，子流可配置如 `/PR1`）。  
   - 关键日志包括：选择的流 profile、实际 `RESULT_VIDEO_SIZE`、decodeType、fallback 原因。

4. **兼容当前低延迟策略**  
   - 保持 AI Vision 低延迟队列与 AI 限频策略；分辨率优化作为上游减压手段与其叠加。

## Risks / Trade-offs

- **[Risk] 摄像头子码流路径不统一** → Mitigation：将子流路径配置化并提供连通性探测与回退。  
- **[Risk] 1080p 录制与 720p 推理同时运行仍抢资源** → Mitigation：监控 CPU/内存与掉帧指标，必要时降低实时 FPS 或调整录制时机。  
- **[Risk] 640x640 误用于显示链路导致拉伸** → Mitigation：明确只用于推理前处理，显示保持原始比例。

## Migration Plan

1. 新增流 profile 配置但默认保持当前行为，分阶段启用双码流。  
2. 先在支持子码流的摄像头灰度验证，再覆盖不支持子码流设备的降级路径。  
3. 若出现稳定性回退，可快速回退到单路主流策略。

## Open Questions

- 当前摄像头型号对子码流 RTSP 路径是否统一（`/PR1` 或其它）？
- 录制链路是否允许独立播放器实例长期占用 1080p 主流？
- 子码流分辨率在 **640×512** 与 **1280×720** 之间如何选择（带宽、观感、推理精度权衡）？
