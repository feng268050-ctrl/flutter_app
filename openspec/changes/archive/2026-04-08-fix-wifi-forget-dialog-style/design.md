## Context

当前 WiFi 详情页的“忘记/断开连接”确认弹窗是独立样式实现，和应用内已存在的统一弹窗视觉体系不一致。用户在设置相关流程中会频繁遇到确认弹窗，样式割裂会降低界面一致性并增加认知成本。该改动仅涉及客户端 UI 资源与弹窗组装逻辑，不改变 WiFi 断开与忘记网络的业务行为。

## Goals / Non-Goals

**Goals:**
- 让 WiFi 忘记确认弹窗与 app 统一弹窗风格对齐，参考设置时区弹窗的视觉模式。
- 统一标题、正文、按钮容器和按钮状态样式，保证暗色主题下可读性和一致性。
- 在不改变现有业务流程的前提下完成 UI 替换，避免引入行为回归。

**Non-Goals:**
- 不修改 `Forget` 操作的业务时序、权限处理或错误处理逻辑。
- 不重构全局弹窗组件体系，仅修复本次 WiFi 流程的风格不一致问题。
- 不新增国际化文案或交互步骤。

## Decisions

- 决策 1：复用设置时区弹窗的样式资源模式，而非继续维护 WiFi 专用样式。  
  理由：已有样式已在产品中验证，能快速实现一致性并降低后续维护成本。  
  备选方案：仅局部调色和圆角微调现有 WiFi 弹窗。未选原因是仍会保留结构差异，无法从根源解决割裂感。

- 决策 2：优先通过布局与 style/theme 引用对齐视觉，而不改变弹窗触发与确认回调接口。  
  理由：将风险限定在 UI 层，减少对网络管理逻辑的回归影响。  
  备选方案：将弹窗创建逻辑整体迁移到新通用组件。未选原因是当前范围过大，超出本次修复目标。

- 决策 3：保留 `Confirm`/`Cancel` 文案与按钮语义，仅统一视觉层级和状态表现。  
  理由：兼容现有规格与测试预期，避免同时引入文案与行为变更。

## Risks / Trade-offs

- [风险] 样式引用对齐后可能影响现有 WiFi 页面控件尺寸或间距。 → [缓解] 在目标分辨率与暗色主题下做对比验收，必要时只覆盖弹窗局部样式。
- [风险] 复用样式资源若依赖特定布局结构，可能出现文本截断或按钮错位。 → [缓解] 对弹窗标题/正文长度和双按钮布局做最小与最大内容验证。
- [权衡] 采用“样式对齐”而非“组件统一”交付速度更快，但全局复用能力有限。 → [缓解] 在后续 UI 治理任务中评估抽象通用确认弹窗组件。
