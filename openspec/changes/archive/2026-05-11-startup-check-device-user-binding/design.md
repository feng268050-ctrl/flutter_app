## Context

应用当前只在启动期处理 WiFi 初始化提醒（未连接时弹框引导设置），尚未在联网就绪后验证设备是否已绑定用户。新增能力要求在启动流程中、WiFi 提醒对话框结束后（若出现）或网络已连接时，调用设备用户列表接口判断绑定状态；当未绑定时，用与 WiFi 提醒一致的视觉风格提示用户扫码绑定。该流程会跨越启动编排、网络状态监听、设备 API 调用层与对话框 UI 复用。

## Goals / Non-Goals

**Goals:**
- 定义单一且可复用的“启动后绑定检查”触发时机，覆盖“有 WiFi 提醒”和“无 WiFi 提醒”两条路径。
- 规范 `GET /v1/devices/:sn/users` 的响应使用方式：按 `ApiResult` 解析，仅消费 `id`、`nickname`、`avatar`、mask 后 `email` 字段用于绑定判断与展示。
- 在用户列表为空时展示扫码绑定提醒对话框，并复用 `Settings -> Device Information -> Machine Model` 的二维码数据源。
- 保证该检查在单次启动流程中幂等，避免重复弹窗。

**Non-Goals:**
- 不在本次变更中改造设备绑定成功后的完整业务流程（例如账号切换、解绑管理）。
- 不新增新的二维码生成协议或后端字段，仅复用现有机型二维码来源。
- 不修改 WiFi 设置页或系统网络连接能力本身。

## Decisions

- 决策 1：将绑定检查挂接到“WiFi onboarding 结束事件”而非任意页面生命周期。
  - Rationale：该事件天然保证“提醒弹窗已处理”或“已连接网络”，满足接口调用前提并减少散落触发点。
  - Alternative：在首页 `onResume` 或 Application 启动回调直接调用；缺点是可能在无网或 WiFi 提醒未完成时重复重试，体验不稳定。

- 决策 2：新增轻量数据模型（例如 `DeviceBindingUserSummary`）承载接口 `data`。
  - Rationale：明确限制字段可避免误依赖冗余用户信息，降低序列化/兼容风险。
  - Alternative：复用完整用户实体；缺点是耦合过深、后续字段变化影响面更大。

- 决策 3：将“空用户列表”定义为未绑定唯一判据，并在本地会话内去重弹窗。
  - Rationale：与后端接口语义直接对齐，且避免网络状态抖动触发多次相同提示。
  - Alternative：依赖本地缓存绑定标记；缺点是缓存过期与跨设备状态不一致风险。

- 决策 4：扫码绑定对话框复用 WiFi 提醒对话框视觉组件/样式 token。
  - Rationale：统一启动引导风格并减少新增 UI 维护成本。
  - Alternative：新增独立弹窗样式；缺点是设计一致性降低、实现成本增加。

- 决策 5：弹窗文案通过 `app` 模块字符串资源维护，键名 `bind_device_dialog_title`、`bind_device_dialog_subtitle`；`values`/`values-en` 为英文源文案，`values-zh` 为简体中文翻译；UI 仅引用 `@string/...`，禁止在代码中硬编码最终展示文案。
  - Rationale：满足多语言与与 WiFi 弹窗一致的资源维护方式。
  - Alternative：远程配置文案；超出本次范围。

## Risks / Trade-offs

- [启动时网络短暂可用但接口失败] → Mitigation：失败仅记录日志并不弹未绑定提示；允许后续合适时机再触发一次检查。
- [网络状态回调与弹窗状态竞争导致重复请求] → Mitigation：增加单次启动幂等标记（如 checking/checked 状态机）串行化请求。
- [二维码来源不可用或加载失败] → Mitigation：回退为仅文字提示并提供进入设备信息页路径，避免空白弹窗。
- [接口返回字段与预期不一致] → Mitigation：解析时按可选字段容错，仍以 `data` 列表长度作为绑定判定。

## Migration Plan

1. 在启动流程编排层引入“绑定检查触发器”，接入 WiFi onboarding 完成事件和网络已连接分支。
2. 在设备 API 层补充/复用 `GET /v1/devices/:sn/users` 调用并映射精简模型。
3. 新增扫码绑定提醒对话框（复用 WiFi 提醒样式），接入机型二维码数据源。
4. 通过特性开关或灰度配置（如项目已有机制）先在测试环境验证，确认无重复弹窗与无网误提示后全量。
5. 回滚策略：关闭启动绑定检查开关或移除触发器调用，保留原 WiFi onboarding 行为不变。

## Open Questions

- WiFi 提醒对话框被用户取消/关闭时，是否仍然立即执行一次绑定检查，还是等待下一次明确联网事件？
- 扫码绑定提醒对话框是否需要“今日不再提醒”一类抑制策略，避免长期未绑定设备每次启动都弹？
- 当接口非空但用户信息字段部分缺失时，弹窗内展示策略是否需要产品文案兜底规范？
