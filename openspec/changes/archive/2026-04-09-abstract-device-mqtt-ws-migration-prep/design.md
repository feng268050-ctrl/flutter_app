## Context

当前设备通信链路将 MQTT topic、报文结构与业务处理逻辑紧耦合在同一层，导致两类问题：一是数据上报与指令下发流程重复处理协议细节，二是协议切换（MQTT 到 WS）会影响大量业务代码。该变更需要在不影响现网 MQTT 能力的前提下，先建立协议无关的领域接口与标准数据模型，为后续 WS 适配器并行开发和灰度切换提供稳定边界。

约束条件：
- 现有设备仍以 MQTT 为主，必须保持行为兼容。
- 对外 API 与业务语义不变，仅重构内部通信分层。
- 迁移阶段需要可观测、可回退、可灰度。

## Goals / Non-Goals

**Goals:**
- 建立设备上报和指令下发的统一通道接口，隔离协议细节。
- 规范内部标准事件/命令模型，统一校验、错误分类与日志字段。
- 通过适配器模式先承载 MQTT，再平滑接入 WS。
- 提供可灰度的协议选择与回退能力，降低切换风险。

**Non-Goals:**
- 本阶段不强制上线 WS 协议传输。
- 不调整业务侧接口契约与终端设备指令语义。
- 不覆盖设备固件端协议升级与兼容策略细节。

## Decisions

1. 采用“领域通道接口 + 协议适配器”分层
- 决策：定义 `DeviceDataChannel` 与 `DeviceCommandChannel` 领域接口，上层只依赖接口；MQTT 实现作为 `Mqtt*Adapter`。
- 原因：把协议切换成本限制在适配器层，避免业务重构。
- 备选：在现有 MQTT 服务内增加条件分支支持 WS。否决原因是分支膨胀且测试边界不清晰。

2. 定义协议无关的标准模型
- 决策：上报统一为 `DeviceDataEvent`，下发统一为 `DeviceCommandRequest/Result`，并要求携带 `deviceId`、`correlationId`、`timestamp`、`sourceProtocol` 等关键字段。
- 原因：保证日志追踪、幂等处理、回执关联在不同协议下保持一致。
- 备选：继续直接传递原始 MQTT payload。否决原因是 WS 接入后会再次出现协议耦合。

3. 统一命令生命周期状态机
- 决策：命令处理统一状态 `accepted -> dispatched -> acknowledged | failed | timeout`，并由通道层产出标准化错误码。
- 原因：为监控告警、重试与回退提供一致语义。
- 备选：由各协议独立定义状态。否决原因是跨协议观测不可比、调用方处理复杂。

4. 引入协议路由与特性开关
- 决策：通过配置/feature flag 为设备或设备组选择协议适配器，默认 MQTT，支持动态回退。
- 原因：支持小范围验证 WS 兼容性，出现异常时快速切回 MQTT。
- 备选：一次性全量切换。否决原因是风险过高。

## Risks / Trade-offs

- [抽象过度导致开发复杂度上升] → 先收敛最小接口集，仅覆盖上报与指令关键路径，避免提前抽象非核心能力。
- [迁移期间双协议并存增加运维负担] → 统一指标、日志字段与 tracing 维度，确保跨协议排障路径一致。
- [回执关联错误导致指令状态不一致] → 强制 `correlationId` 贯穿请求与回执，并增加超时与重复回执处理规则。
- [灰度配置错误影响设备通信] → 增加协议路由配置校验、默认兜底 MQTT、提供一键回退。

## Migration Plan

1. 提取当前 MQTT 上报与下发逻辑中的领域处理代码，沉淀为协议无关服务。
2. 定义并接入 `DeviceDataChannel` / `DeviceCommandChannel` 接口及标准模型。
3. 将现有 MQTT 能力迁移至 `Mqtt*Adapter`，在回归测试中验证行为等价。
4. 引入协议路由配置与监控指标，默认全量走 MQTT（仅重构，不改传输协议）。
5. 在后续独立变更中实现 WS 适配器并进行小流量灰度。
6. 如出现异常，使用 feature flag 将受影响设备快速切回 MQTT。

## Open Questions

- WS 适配器阶段是否需要与 MQTT 并行双写/双收做一致性校验，还是仅灰度单通道验证？
- 设备离线缓存与重连补发逻辑由通道层统一处理，还是保留在各协议适配器内？
- 指令超时阈值和重试策略是全局统一，还是按设备类型可配置？
